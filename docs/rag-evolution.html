COREX — Retrieval Architecture Evolution

How the general-module's retrieval pipeline changed over four iterations. Each stage solved the problem the previous one couldn't, and traded off something the next one fixed.

Iteration 1

Retrieval + LLM Reranker

Archived
How it worked

Retriever cast a wide net (top-50 by vector similarity), then a second LLM call re-ranked those candidates by actual relevance to the ticket. The synthesizer only saw the top few survivors.

Why we moved on

Reranker added a full extra LLM hop per query — slow and expensive — but couldn't fix bad retrieval, only re-sort it. If the right chunk wasn't in the top-50, reranking didn't help.

Iteration 2

Hybrid RAG (BM25 + RRF)

Archived
How it worked

Lexical retrieval (BM25) ran against multiple query variants for the same ticket, and the ranked lists were merged with reciprocal rank fusion. Docs ranking high across several phrasings floated to the top.

Why we moved on

Lexical-only hybrid handled error codes and exact strings well but missed rephrased questions. The added complexity of merging multiple rankings didn't earn its keep once we had a smarter agent that could decide what to fetch.

Iteration 3

Self-RAG (Verifier Loop)

Archived
How it worked

After drafting an answer, a separate verifier LLM checked whether the draft actually grounded its claims in the retrieved chunks. If not, it looped back and retrieved again with a refined query.

Why we moved on

The loop guarded against hallucinations but at 2–3× the cost. The verifier was effectively a planner — so we moved the planning before retrieval (let the model choose what to fetch) rather than checking after.

Iteration 4

Tool-Using Agent

Current
How it worked

No fixed pipeline. The model itself decides what to retrieve and when to stop. Three tools available: semantic search (dense, 1536-D embeddings, 5–10 chunks per call), exact-text grep, and full article read.

Vectors sent per ticket

~5–60 chunks total (5–10 per call × up to 6 tool calls). Most tickets resolve in 1–2 calls, so the typical model sees 5–20 chunks out of 4,642.

Why it stuck

Retrieval becomes adaptive — easy tickets need one search, hard ones can grep for an error code then expand to the full article. One model in the loop instead of three. Currently in production.

KB index: 4,642 chunks · 1,536-D embeddings · text-embedding-3-small · Tool default k=5, max k=10 per call, up to 6 calls per ticket.
